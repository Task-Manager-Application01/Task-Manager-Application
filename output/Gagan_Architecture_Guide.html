Project overview

This is a multi-workspace task management application built for PES University Software Engineering. Team members sign in, work inside workspaces, manage tasks and subtasks, and monitor progress using a Kanban board, search and analytics.

Run and demonstrate

Start the server

Install Node.js 18 or newer, open a terminal in the project folder and run:

npm start

Keep that window open. The default address is http://localhost:3000. Open /health to check the server, /kanban for the board and /analytics for analytics. PORT changes the listening port.

Create sample data

Open a second terminal in the same folder and run:

npm run demo

The demo requires the server to be running. It creates a user with a generated email such as demo<timestamp>@pes.edu, shown in its output, and password Passw0rd!x. It creates a workspace and sample task. The Kanban page also contains registration and workspace creation forms in the current checkout.

Try your features

Sign in, select or create a workspace, create tasks with tags, then move cards between columns. In search, type a keyword, or enter comma-separated tags and values such as high, review. Select sort field and order. Search updates after a short pause. For reports, use the CSV/PDF export buttons. The analytics page has its own login.

To apply backend changes, stop the server with Ctrl+C and run npm start again; refresh the browser. npm test runs the Node tests. Configure a strong JWT_SECRET outside demo use.

Router: selects code based on URL and HTTP method. Controller: typically receives request data and sends a response. Service: contains feature or business logic. Some routes call services directly rather than going through a separate controller.

For example, a task move goes browser → POST /tasks/:id/move → requireTaskAccess → taskDragDrop.moveCard → Database.js, event broadcast, audit and notifications → JSON response.

Actual stack: Node's built-in HTTP server, plain HTML/CSS/JavaScript and a JSON-backed store. The SRS/SAD may describe React, Express or PostgreSQL; consult docs/SPRINT1_DEVIATIONS.md and the current code for differences.

Core entities: user; workspace; membership connecting a user to a workspace with a role; task belonging to a workspace with status, priority, assignees and tags; subtask and attachment metadata belonging to a task; notification and audit entry. Authentication, workspace and tasks

Registration and login are handled by authController. Passwords use salted PBKDF2; a signed JWT identifies the logged-in user. The browser sends Authorization: Bearer <token>. The router rejects protected calls without a valid token. RBAC checks role and workspace membership: Admin and Member can contribute; Viewer can view. Workspace creation automatically assigns the creator as Admin.

TaskController handles task creation, viewing, editing, archive and permanent deletion. SubtaskController handles subtask operations; completed subtasks affect the stored progress percentage. Attachments in this implementation validate and store metadata, not actual file bytes. Email delivery is a logging stub; invitation and reset tokens are not delivered by a real mail service.

Request flow: frontend collects form values; app.js parses JSON and the token; a controller validates and invokes database/service functions; response JSON goes back to the browser. Workspace membership restricts access to the correct team.

Your part A: Kanban board

A Kanban board groups tasks into To-Do, In-Progress, Review and Done. Each task stores a status; there is no separate database table per column. The browser requests GET /api/v1/workspaces/:workspaceId/kanban; app.js verifies workspace access and invokes getKanbanBoard(workspaceId).

  1. Fetch active tasks belonging to the workspace.
  2. Create an array for each of the four statuses.
  3. For each task, look at its status and append it to the matching array.
  4. Look up assigned users and include names and initials as avatar data.
  5. Return the grouped object for the browser to render.

The taskDragDrop service is the backend implementation; the board DOM and drag events live in src/public/kanban.html. The result contains enriched task objects; the original task is not permanently changed merely by building the board.

Your part B: moving a task

When a user moves a card, the page makes an optimistic update: it changes the displayed board immediately, sends POST /api/v1/tasks/:taskId/move, and restores the snapshot if the request fails. The request body contains {"targetColumn":"In-Progress"}. The actor ID comes from the authenticated token.

  1. The router checks write access to the task's workspace.
  2. moveCard checks the target is a valid status and finds the task.
  3. If old and new statuses are equal, it returns transitioned: false.
  4. Otherwise it updates status, publishes task.moved, records an audit event and notifies assignees other than the actor.
  5. It returns the updated task and both statuses.

These are separate operations, not a single database transaction. The backend publishes server-sent events to workspace subscribers; the notification/audit page refreshes through polling, so do not describe the complete interface as instant push.

Your part C: assignment

Assignment answers who is responsible for a task. POST /api/v1/tasks/:taskId/assign accepts {"userIds":["user-1","user-2"]}. The router checks the actor's write access; assignCollaborators checks the task exists and the IDs are supplied as an array.

For each ID, rbacService.isMember checks membership of that task's workspace. If an outsider is included, the service throws before updating. On success it replaces the task's assignee array, creates assignment notifications and writes an audit entry.

Important: the supplied list replaces existing assignees; send all people who should remain assigned. An empty array clears the assignment. The backend route exists; verify whether the current UI exposes an assignment control before promising an in-browser demo.

Your part D: keyword search and tags

The page requests GET /api/v1/search/tasks with workspace_id, q, tags and sort parameters. The route verifies workspace membership. The frontend fetches matching IDs and filters the board cards; sorting is applied inside each status column. Search inputs are debounced for 300 ms.

Keyword search

queryTasks scans tasks and uses lowercase includes() against title, description and tag labels. This is case-insensitive substring search in JavaScript, not an indexed database full-text search engine. Searching 'login' finds 'Login page'.

Composite filters

Tags are comma-separated and every entered filter must match. The tags field also recognises priority values High, Medium and Low, and workflow labels such as review / in review, to do, in progress and done. Example: high, review matches a High-priority task in Review. Actual task tags also match. Keyword and tag criteria combine with AND. Task creation/editing accepts comma-separated task tags.

The backend also accepts priority, status, assignee and due-date filters, but not every backend filter has a corresponding UI control. Date filters exclude undated tasks. Avoid confusing the separate workspace coloured-tag catalog with tag strings stored on tasks.

Your part E: sorting and routes

queryTasks sorts by created_at, due_date, priority or title. High, Medium and Low map to 3, 2 and 1. Ascending keeps the comparator direction; descending reverses it. The default is creation date descending. No due date is put last in either direction. Search returns total, execution_time_ms and matching data.

Analytics and report exports

AnalyticsService computes total, completed, overdue, completion rate and team velocity. Velocity uses tasks currently Done whose updated_at falls inside the selected window: (count / sprintDays) * 7, rounded to one decimal. It is an estimate, not a recorded history of completion events; editing a completed task can change updated_at.

The analytics page displays status distribution, member workload and a completion bar, plus the calculated tasks-per-week figure. Workload counts assigned and completed tasks per member. It uses the distribution and KPI endpoints.

ReportExporter produces CSV and PDF. Completed tasks are displayed as 100% in both exports; other tasks use their stored progress. PDF uses exportToDocumentSummary and a simple built-in PDF writer. CSV includes archived tasks; document summary/PDF uses active tasks. Non-Latin characters may not render correctly in the PDF's built-in font.

Notifications, audit and timing

The deadline scheduler checks open tasks due within the next 24 hours (including overdue tasks) and creates a notification for each assignee, suppressing repeats for 24 hours. It runs at startup and then hourly by default. The current Kanban interface polls notifications and workspace audit activity every 10 seconds; users can mark their notifications read. The scheduler is periodic, so this is not an exact deadline-time push.

Audit records contain workspace, actor, action, target, details and timestamp. Entries are frozen in memory and there is no normal audit editing API, but data is stored in a local JSON file that can be modified by someone with file access. It is not a tamper-proof immutable audit system.

Backend task-move SSE is separate from feed polling: realtimeService keeps workspace subscriber connections and publishes task.moved events. Open streams are checked for workspace access, and can be disconnected on membership removal.

Viva preparation and limitations

What did your assigned feature set cover? Kanban task grouping and movement, collaborator assignment, searching, filtering, sorting and tags.

How does multi-tag filtering work? Every supplied filter must match a task tag or a recognised priority/status. Keyword criteria are also applied.

How do you prevent assigning an outsider? Check each requested ID with rbacService.isMember before updating the task.

What happens on a move? Validate status and access, update task, publish the move event, create audit log and notify other assignees.

What is the actual persistence technology? In-memory JavaScript collections persisted as JSON snapshots, not a relational or MongoDB server.

Is keyword search a database full-text index? No; it scans task strings with case-insensitive substring checks.

Are the audit logs tamper-proof? No; normal operations append records, but local file access can alter the JSON.

What should be checked before presenting? Run npm test and demonstrate the current browser workflow locally. In the inspection environment, HTTP tests were blocked by local network permissions, so browser end-to-end behaviour has not been independently verified here.
